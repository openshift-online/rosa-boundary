# HCP Terraform workspace integration

This page describes **public-repository-backed configuration and onboarding steps**, not a live HCP run or AWS inventory. It deliberately omits personal accounts, individual service-account ownership and private discussion links. The tenant bootstrap and reusable modules live in [openshift-online/infra-platform](https://github.com/openshift-online/infra-platform); the project-specific meta-workspace and AWS workloads live here. For resource-level details see [regional infrastructure](regional-runtime.md); for the operational walkthrough see [`docs/staging-deployment.md`](../../docs/staging-deployment.md); for the IAM/OIDC trust model see [identity and access](../architecture/identity-and-access.md). Recheck Git and HCP before making changes.

## What was set up, and in which account

| Account | Role in staging/production setup | Access boundary |
|---|---|---|
| `rosa-boundary-stage` (`150100906299`) | Long-lived staging account: HCP federation, shared account roles, and separate network/runtime states in `us-east-1` and `us-west-2` | The [staging AWS credentials stack](../../hcp-terraform/aws-creds/rosa-boundary-stage/main.tf) guards the account with `allowed_account_ids = ["150100906299"]` and targets the `hp-platform-engineering` HCP organization. Its `default` role group allowlists all six staging L3 workspaces. Trusted Actions uses a different role group, not Boundary's plan-role permissions. |
| `rosa-boundary-prod` (`514903006123`) | A **separate** production AWS account, distinct from staging, now registered with the same six-workspace topology as staging | The [production AWS credentials stack](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf) guards this account with `allowed_account_ids = ["514903006123"]` ([L17-L20](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf#L17-L20)). Its `default` role group now allowlists all six registered production workspaces: `rosa-boundary-prod-aws-creds`, `rosa-boundary-prod-account`, `rosa-boundary-prod-network-us-east-1`, `rosa-boundary-prod-regional-us-east-1`, `rosa-boundary-prod-network-us-west-2`, and `rosa-boundary-prod-regional-us-west-2` ([L38-L45](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf#L38-L45)) -- a full `us-east-1`/`us-west-2` network-and-regional pair now exists in each region, mirroring staging's Region A/Region B split. Only the credentials workspace itself still requires manual apply confirmation (see [Production: a second, separate AWS account now at staging parity](#production-a-second-separate-aws-account-now-at-staging-parity)). |
| Other environments | Not part of this deployment | Local `.env`, Makefiles, and tfvars are for local development, not HCP runs. CI and real-infrastructure testing must not be mistaken for either account's HCP runtime. See [the quickstart](../quickstart.md) for local developer setup. |

Each [network-root](../../deploy/network/) instance defines a dedicated VPC, private subnets, NAT egress, and an S3 gateway endpoint; both staging and production now have two (`us-east-1`, `us-west-2`). Both accounts' east workspaces use the root's east-region defaults; both accounts' west workspaces explicitly select `us-west-2`, two west-region AZs, a separate CIDR range, and single-NAT routing. Consult network outputs and the matching [regional workspace inputs](../../hcp-terraform/rosa-boundary/main.tf) for actual IDs; Backplane allowlisting is a separate network concern, not an HCP permission grant. All regional definitions -- staging and production alike -- use the Red Hat EmployeeIDP issuer (`auth.redhat.com`, `ai-sd-sre` role/group, `uuid` ABAC key), separate from the `app.terraform.io` OIDC provider used for Terraform's AWS credentials.

## Onboarding sequence and permissions

1. **Separate AWS account provisioning from Terraform deployment.** Each AWS account is a prerequisite for HCP Terraform; this repository declares the account ID as a provider guard but does not provision the AWS account itself. HCP onboarding is defined in [infra-platform's ROSA tenant configuration](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/rosa/main.tf), not via app-interface `terraform-repo`.
2. **Bootstrap the tenant (L1).** [infra-platform PR #56](https://github.com/openshift-online/infra-platform/pull/56) established the tenant bootstrap and [#80](https://github.com/openshift-online/infra-platform/pull/80) registered the `rosa-boundary` project and meta-workspace. The [`rosa-bootstrap` definition](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/rosa/main.tf) grants the SSO-mapped `ai-sd-sre` team admin access to the bootstrap workspace and the `meta-rosa`/`rosa-boundary` projects, and attaches the deletion-protection policy set. The initial bootstrap run requires platform-admin credentials; project access does not confer AWS access by itself. A new AWS account (such as production) reuses this same `rosa-boundary` project rather than requiring a new L1 project.
3. **Grant VCS access.** The **Terraform Cloud GitHub App** is the HCP Terraform VCS connection for `openshift-online/rosa-boundary`, as declared in the [L1 project](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/rosa/main.tf) and [L2 workspace definitions](../../hcp-terraform/rosa-boundary/main.tf). The org's App installation must include the repository; the account authorizing the integration needs effective repository **Read** access and an HCP identity. Installation and repository access are distinct from HCP project permissions. See the [infra-platform onboarding guide](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/README.md). This is **not** the ROSA BOUNDARY CI GitHub App used by image builds.
4. **Register the meta-workspace (L2).** [Boundary PR #111](https://github.com/openshift-online/rosa-boundary/pull/111) provided the minimal `hcp-terraform/rosa-boundary` scaffold before the L1 configuration pointed a VCS-connected workspace at it. L1 attaches the `rosa-admin-creds` TFE API credential variable set and notification variable set to `meta-rosa-rosa-boundary`; review live variable-set ownership and rotation outside this public wiki. L2 owns the Git-managed L3 workspace definitions and input bindings for **every** AWS account's workspaces, staging and production alike. Do not publish token or webhook values.
5. **Bootstrap AWS dynamic credentials, then workloads (L3).** [Boundary PR #147](https://github.com/openshift-online/rosa-boundary/pull/147) introduced staging's network/credentials workspaces with a minimal network scaffold; [#153](https://github.com/openshift-online/rosa-boundary/pull/153) fixed the TFE provider configuration. [#154](https://github.com/openshift-online/rosa-boundary/pull/154) defined the HCP OIDC provider, phase-scoped AWS plan/apply roles and project variable set, followed by [#164](https://github.com/openshift-online/rosa-boundary/pull/164) and [#165](https://github.com/openshift-online/rosa-boundary/pull/165) for workspace binding. [#173](https://github.com/openshift-online/rosa-boundary/pull/173) introduced the VPC resources after the workspace existed. Regional infrastructure followed in [#182](https://github.com/openshift-online/rosa-boundary/pull/182), [#190](https://github.com/openshift-online/rosa-boundary/pull/190), and [#192](https://github.com/openshift-online/rosa-boundary/pull/192). The production account followed the same sequence: its credentials and account workspaces bootstrapped first (comments in the L2 map reference a `T3-PR5`/`T3-PR6` sequence), and its `us-west-2` network/regional pair has since been registered too, completing parity with staging (a `T3-PR8 (#428)` network-apply output now backs the west regional workspace's VPC/subnet inputs); see [Production: a second, separate AWS account now at staging parity](#production-a-second-separate-aws-account-now-at-staging-parity) below. For a new workspace, **merge an empty scaffold before registration**: the initial run may not respect an ordinary manual-apply gate. Follow the public [tenant onboarding guide](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/README.md) and [dynamic credentials guide](https://github.com/openshift-online/infra-platform/blob/main/docs/aws-dynamic-creds.md) rather than copying a person's bootstrap credentials.

## Ownership and why there are multiple workspaces

```mermaid
flowchart TD
    L1["infra-platform: rosa-bootstrap (L1, Default project)"] --> L2["rosa-boundary: meta-rosa-rosa-boundary (L2, meta-rosa project)"]
    L2 --> C1["rosa-boundary-stage-aws-creds (L3, stage AWS creds)"]
    L2 --> A1["rosa-boundary-stage-account (L3, stage shared identities)"]
    L2 --> N1["rosa-boundary-stage-network (L3, us-east-1 network)"]
    L2 --> N2["rosa-boundary-stage-network-us-west-2 (L3, us-west-2 network)"]
    L2 --> R1["rosa-boundary-stage-regional (L3, us-east-1 runtime)"]
    L2 --> R2["rosa-boundary-stage-regional-us-west-2 (L3, us-west-2 runtime)"]
    L2 --> C2["rosa-boundary-prod-aws-creds (L3, prod AWS creds, manual apply)"]
    L2 --> A2["rosa-boundary-prod-account (L3, prod shared identities)"]
    L2 --> N3["rosa-boundary-prod-network-us-east-1 (L3, prod us-east-1 network)"]
    L2 --> R3["rosa-boundary-prod-regional-us-east-1 (L3, prod us-east-1 runtime)"]
    L2 --> N4["rosa-boundary-prod-network-us-west-2 (L3, prod us-west-2 network)"]
    L2 --> R4["rosa-boundary-prod-regional-us-west-2 (L3, prod us-west-2 runtime)"]
```

L1 to L2 to L3 ownership chain: one meta-workspace manages twelve L3 workspaces split evenly across the `150100906299` staging account and the `514903006123` production account; only `rosa-boundary-prod-aws-creds` still requires manual apply confirmation.

Each box is a separate HCP Terraform workspace with its **own state and run history**. A working directory is a source-code choice, not a state identity: all four `-network*` workspaces (two staging, two production) use `deploy/network`, all four `-regional*` workspaces use `deploy/regional`, and `rosa-boundary-prod-account` reuses the very same `deploy/account` directory as `rosa-boundary-stage-account` -- three directories, twelve states. L1 owns HCP project/team setup; L2 owns project-workspace configuration through the TFE API; the L3 workspaces partition AWS concerns per account. Each account's credentials workspace owns that account's HCP OIDC provider, plan/apply roles, and HCP variable sets. Network states own their VPC/subnets/routing -- two per account now. **One account workspace per AWS account owns that account's shared IAM identities, common managed-policy attachments, user OIDC provider(s), Bedrock budget, and model agreements**. Regional states consume their respective VPC/subnet IDs and own ECS, EFS, Lambda, regional inline IAM policies, KMS, and audit infrastructure; production's two regional workspaces are registered with concrete VPC/subnet/image inputs wired in and, unlike the credentials workspace, both auto-apply -- but `auto_apply = true` is still not proof of a completed apply on its own, so check live run history rather than assuming from Git alone. See the [L2 map](../../hcp-terraform/rosa-boundary/main.tf) and [account ownership guide](../../deploy/account/README.md). Separate states are not separate AWS accounts by themselves -- but in this case the production workspaces genuinely are a separate AWS account, not merely a separate state in the same one; Git alone does not prove an applied migration.

The bootstrap module creates the `rosa-boundary` and `meta-rosa` projects, `ai-sd-sre` team access, and the `rosa-deletion-protection` policy set over the bootstrap and both projects; its project map creates `meta-rosa-rosa-boundary` and connects it to `openshift-online/rosa-boundary`. The private registry modules are version-pinned by **each caller**: the Boundary meta-workspace calls the `workspaces/tfe` module at `0.0.23` ([L16-L18](../../hcp-terraform/rosa-boundary/main.tf#L16-L18)), both credentials stacks call `aws-dynamic-creds/tfe` at `0.0.15`, and the L1 bootstrap module is separately pinned at `0.0.23`; changing upstream module source alone does not upgrade the deployed callers. This single `rosa_boundary` module call now declares all twelve L3 workspaces -- six in `rosa-boundary-stage` ([L36-L706](../../hcp-terraform/rosa-boundary/main.tf#L36-L706)) and six in `rosa-boundary-prod` ([L709-L1394](../../hcp-terraform/rosa-boundary/main.tf#L709-L1394)). `cloud.tf` in each control-plane/credentials directory names its own HCP workspace -- staging's and production's `aws-creds` directories each have a distinct `cloud.tf`. The network, account and regional directories are run by their VCS-connected L3 workspaces; local `.env`, `terraform.tfvars`, Makefile and local state are for development, not inputs to the HCP runs.

## Bootstrap order and credential handoff

1. **Tenant and L1:** The HCP GitHub App must be able to read both repositories. The platform team first merged a minimal `infra-platform/hcp-terraform/tenants/rosa` directory, created `rosa-bootstrap` in the Default project with platform variable sets, and manually queued its first run. Its full config then manages that workspace via import and creates the `meta-rosa` project, the `rosa-boundary` project, the team/policies, and the L2 workspace. See the [infra-platform onboarding guide](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/README.md) for the general bot and initial-run sequence. L1 does **not** provision Boundary's AWS resources, staging or production.
2. **L2:** Its working directory must already be on `main` before L1 creates the VCS-connected meta-workspace. L1 attaches tenant-level TFE/notification variable sets and uses `tfe_workspace_run` for the initial L2 run. L2's TFE provider then creates every L3 workspace it declares -- across both AWS accounts -- attaches their project-scoped variable sets, sets their Terraform variables, and queues first runs via the workspaces module.
3. **AWS identity bootstrap:** Each account's credentials workspace needs AWS access to create its own HCP OIDC provider, IAM roles and dynamic-credentials variable set. The historical staging bootstrap used the payer-assumed admin role; [upstream dynamic-credentials guide](https://github.com/openshift-online/infra-platform/blob/main/docs/aws-dynamic-creds.md) documents alternatives and handoff. Each account's final L2 definition attaches `rosa-boundary-tfe-creds` and that account's generated AWS set; do not put tokens or static keys into Git. See the [staging credentials module](../../hcp-terraform/aws-creds/rosa-boundary-stage/main.tf) and the [production credentials module](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf).
4. **Workloads:** The staging AWS-credentials module's `default` role group explicitly lists all six staging Boundary workspaces in the `rosa-boundary` project, including both `-us-west-2` entries. The production AWS-credentials module's `default` role group now lists all six registered production workspaces -- `rosa-boundary-prod-aws-creds`, `rosa-boundary-prod-account`, `rosa-boundary-prod-network-us-east-1`, `rosa-boundary-prod-regional-us-east-1`, `rosa-boundary-prod-network-us-west-2`, and `rosa-boundary-prod-regional-us-west-2` -- in its `workspace_names` allowlist ([L38-L45](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf#L38-L45)), so both east- and west-region production workloads are now authorized for AWS federation, not just the east pair. Its inline comment, "Authorize workload workspaces separately after registration," reflects the account's bootstrap history rather than a remaining gap: all four workload workspaces (both regions' network and regional stacks) already appear in the allowlist today, so treat such comments as provenance, not as current-state proof -- verify the live list rather than trusting a comment that may predate a later addition. L2 attaches each account's generated AWS variable set to that account's own workspaces only; a staging workspace is never bound to the production set or vice versa. Both IAM trust allowlisting **and** variable-set binding are required; adding a workspace definition or binding alone does not authorize AWS federation. Each network workspace outputs `vpc_id` and `private_subnet_ids`; its regional counterpart receives these as explicit Git-managed L2 workspace variables, **not** through remote state or a network→regional run trigger -- both of production's regional workspaces already have concrete `vpc_id`/`subnet_ids` values copied in this way, annotated as network-apply outputs. Verify the correct region's network inputs before regional runs.

Trusted Actions is intentionally separate: the staging credentials stack declares a `rosa-trusted-actions` role group for `rosa-trusted-actions-global` and `rosa-trusted-actions-stage`. Its plan role adds a narrowly scoped `secretsmanager:GetSecretValue` policy to `ReadOnlyAccess` because refreshing a secret version requires that read even with `ignore_changes`. The addition does **not** widen Boundary's default plan role. Apply-role policy defaults are unchanged. [Role groups and scoped plan policy](repo://hcp-terraform/aws-creds/rosa-boundary-stage/main.tf#L25-L85).

The HCP OIDC provider is for **Terraform's AWS provider**, distinct from the Boundary user's Keycloak OIDC federation described in [identity and access](../architecture/identity-and-access.md). The upstream [AWS dynamic-credentials module](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/modules/terraform-tfe-aws-dynamic-creds/main.tf) restricts `app.terraform.io:aud` and `sub` to organization/project/workspace/run phase; by default the plan role has AWS `ReadOnlyAccess`, and the apply role has `AdministratorAccess`. It writes `TFC_AWS_PROVIDER_AUTH`, `TFC_AWS_PLAN_ROLE_ARN` and `TFC_AWS_APPLY_ROLE_ARN` into the project-scoped set, once per AWS account. Each credentials workspace additionally uses a TFE token to manage HCP resources; workload workspaces need only their own account's AWS set. The AWS provider in each credentials stack checks its own expected account ID (`150100906299` for staging, `514903006123` for production), as do the staging and production network and regional providers.

## Production: a second, separate AWS account now at staging parity

The L2 map now defines **six** production L3 workspaces inside the same `rosa-boundary` HCP project, exactly mirroring staging's six: `rosa-boundary-prod-aws-creds` ([L709-L722](../../hcp-terraform/rosa-boundary/main.tf#L709-L722)), `rosa-boundary-prod-account` ([L726-L905](../../hcp-terraform/rosa-boundary/main.tf#L726-L905)), `rosa-boundary-prod-network-us-east-1` ([L909-L961](../../hcp-terraform/rosa-boundary/main.tf#L909-L961)), `rosa-boundary-prod-regional-us-east-1` ([L965-L1132](../../hcp-terraform/rosa-boundary/main.tf#L965-L1132)), `rosa-boundary-prod-network-us-west-2` ([L1136-L1216](../../hcp-terraform/rosa-boundary/main.tf#L1136-L1216)), and `rosa-boundary-prod-regional-us-west-2` ([L1219-L1394](../../hcp-terraform/rosa-boundary/main.tf#L1219-L1394)). None of them target staging's AWS account: [`hcp-terraform/aws-creds/rosa-boundary-prod/main.tf`](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf) guards its AWS provider with `allowed_account_ids = ["514903006123"]` ([L17-L20](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf#L17-L20)), a distinct account from staging's `150100906299`, and [`cloud.tf`](../../hcp-terraform/aws-creds/rosa-boundary-prod/cloud.tf) names its own `rosa-boundary-prod-aws-creds` HCP workspace. The module instance's `aws_account_name = "rosa-boundary-prod"` ([L31](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf#L31)) keeps its generated dynamic-credentials set and role ARNs entirely independent of staging's.

Trust now covers the full six-workspace production workload set. The production credentials stack's `role_groups.default.projects.rosa-boundary.workspace_names` allowlists all six workspace names: `rosa-boundary-prod-aws-creds`, `rosa-boundary-prod-account`, `rosa-boundary-prod-network-us-east-1`, `rosa-boundary-prod-regional-us-east-1`, `rosa-boundary-prod-network-us-west-2`, and `rosa-boundary-prod-regional-us-west-2` ([L38-L45](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf#L38-L45)). ## Two regions, one shared identity contract

Both staging regional definitions set `account_role_name_prefix = "rosa-boundary-stage"` and `legacy_policy_region = "us-east-1"`. Only east retains unsuffixed inline-policy names; west appends `-us-west-2` instead of overwriting east's policies on the shared roles. Never independently designate west as a second legacy owner. The account root's [handoff outputs](repo://deploy/account/outputs.tf#L1-L12) define this contract, and the [regional naming logic](repo://deploy/regional/account-iam.tf#L1-L8) implements it. Permissions on shared roles are the union of regional grants, not a region-isolation boundary. Production's account workspace sets the equivalent `legacy_policy_region = "us-east-1"` for itself ([L766-L782](../../hcp-terraform/rosa-boundary/main.tf#L766-L782)), and **both** of its regional workspaces independently set the matching `account_role_name_prefix = "rosa-boundary-prod"` and `legacy_policy_region = "us-east-1"` -- east at [L976-L988](../../hcp-terraform/rosa-boundary/main.tf#L976-L988) with a comment warning that "every other production region must keep this same value," and west at [L1236-L1248](../../hcp-terraform/rosa-boundary/main.tf#L1236-L1248) with a matching comment to "keep us-east-1 as the legacy policy region so Region B uses region-suffixed IAM inline policies without conflicting with Region A." Production's west regional workspace is now live proof that the contract holds across a second region exactly as designed: `us-east-1` remains the sole legacy owner in both AWS accounts, and `us-west-2` always takes the suffix, never a second unsuffixed identity.

The staging account input explicitly approves `us-east-1` and `us-west-2` in `bedrock_logging_source_regions`. This extends the Bedrock delivery role's `SourceArn` trust only to those regions while retaining its `SourceAccount` restriction; regional roots still own their own logging destinations and inline delivery grants (see [audit and logging](../operations/audit-and-logging.md) for the logging pipeline itself). Account state also owns the investigation reaper's basic/VPC managed-policy attachments, so a second region must not claim the same shared attachment. The staging L2 account input disables `adopt_existing_resources`; this is not an instruction to re-enable adoption for an additional region. Review live state and plans rather than interpreting leftover migration approvals or comments as proof of ownership transfer. [Staging account inputs](repo://hcp-terraform/rosa-boundary/main.tf#L153-L328) · [logging trust](repo://deploy/account/modules/shared-iam/bedrock-logging.tf#L1-L28) · [reaper attachments](repo://deploy/account/modules/shared-iam/lambda-reap-investigations.tf#L1-L19).

## What causes a plan, and what applies it

There are **two independent event paths**, not just a single linear cascade:

| Event | Plan/run behavior | Apply behavior |
|---|---|---|
| Upstream-branch PR changing a workspace's VCS working directory (or configured trigger prefix) | HCP's GitHub App creates a **speculative plan** for an already initialized matching workspace; inspect the PR checks. Fork PRs do not reliably receive those plans. | A speculative plan is review-only; it does not apply. |
| Merge to `infra-platform` `main` changing `hcp-terraform/tenants/rosa` or its `hcp-terraform/policies` trigger prefix | VCS queues `rosa-bootstrap`; changes elsewhere in infra-platform do not automatically plan this tenant merely because a private registry module's source changed. | Bootstrap `auto_apply` defaults to true. Successful bootstrap apply feeds a `tfe_run_trigger` targeting L2; L2's own VCS connection to Boundary can also independently cause a run. |
| Merge to `rosa-boundary` `main` changing `hcp-terraform/rosa-boundary` | VCS queues L2. | L2's bootstrap-managed `auto_apply` defaults to true; it reconciles workspace configuration and its successful apply can trigger **every** L3 workspace it owns -- staging and production -- even when no files changed in their directories. |
| Merge to `rosa-boundary` `main` changing `deploy/network`, `deploy/account`, `deploy/regional`, `hcp-terraform/aws-creds/rosa-boundary-stage`, or `hcp-terraform/aws-creds/rosa-boundary-prod` | Matching L3 VCS connections queue runs without an L1/L2 change. All three shared working directories now span both AWS accounts: `deploy/network` is used by all four network workspaces (two staging, two production); `deploy/regional` is used by all four regional workspaces; `deploy/account` is used by `rosa-boundary-stage-account` **and** `rosa-boundary-prod-account`. A single PR touching any of these three directories can therefore queue runs in **both** AWS accounts at once. | **Eleven of the twelve** L3 workspaces set `auto_apply = true` and `auto_apply_run_trigger = true`. All six staging workspaces do so, either explicitly (`rosa-boundary-stage-network-us-west-2` at [L76-L77](../../hcp-terraform/rosa-boundary/main.tf#L76-L77), `rosa-boundary-stage-account` at [L158-L159](../../hcp-terraform/rosa-boundary/main.tf#L158-L159), `rosa-boundary-stage-regional` at [L335-L336](../../hcp-terraform/rosa-boundary/main.tf#L335-L336), `rosa-boundary-stage-regional-us-west-2` at [L528-L529](../../hcp-terraform/rosa-boundary/main.tf#L528-L529)) or by omitting the override and inheriting the called module's default (`rosa-boundary-stage-network`, `rosa-boundary-stage-aws-creds`). Five of the six production workspaces now do the same, explicitly: `rosa-boundary-prod-account` ([L732-L733](../../hcp-terraform/rosa-boundary/main.tf#L732-L733)), `rosa-boundary-prod-network-us-east-1` ([L915-L916](../../hcp-terraform/rosa-boundary/main.tf#L915-L916)), `rosa-boundary-prod-regional-us-east-1` ([L971-L972](../../hcp-terraform/rosa-boundary/main.tf#L971-L972)), `rosa-boundary-prod-network-us-west-2` ([L1142-L1143](../../hcp-terraform/rosa-boundary/main.tf#L1142-L1143)), and `rosa-boundary-prod-regional-us-west-2` ([L1225-L1226](../../hcp-terraform/rosa-boundary/main.tf#L1225-L1226)). **`rosa-boundary-prod-aws-creds` is now the only workspace in the repository that explicitly disables this**: `auto_apply = false` and `auto_apply_run_trigger = false` ([L715-L716](../../hcp-terraform/rosa-boundary/main.tf#L715-L716)), combined with `execution_mode = "remote"` -- every ordinary apply to that one workspace needs manual confirmation, while every ordinary apply everywhere else, staging or production, does not. |
| A newly registered L2 or L3 workspace | The owning module's `tfe_workspace_run` queues an **initial** run after workspace settings, variables, bindings and policies; this is distinct from the ordinary run triggers. | The module's initial apply block has `manual_confirm = false`; review readiness and dependencies **before** creating the workspace. |

Run triggers are installed **on the downstream workspace**: bootstrap→meta in the upstream bootstrap module; meta→each L3 in the upstream workspaces module. `source_workspaces` can add further upstream sources, but the present L2 map does not declare any. In particular, there is no network→regional trigger and no guaranteed execution order between L3 siblings, staging or production. VCS working-directory filtering and run triggers can both produce runs for a commit; review run source and state rather than assuming exactly one run. `queue_all_runs = false` is set by both modules for managed downstream workspaces. A failed plan, invalid credentials, policy denial, or missing input does not become an apply; `auto_apply = true` is **not** a promise that every change deploys, and `auto_apply = false` is not by itself proof that a human reviewed a change -- it only means the run stops short of applying until someone confirms it. The `rosa-deletion-protection` OPA policy requires a matching unexpired `_deletion_approvals` entry for deletes; policy overrides, where permitted, are a separate deliberate action. Slack notification setup includes runs needing attention and errors, not just successful runs.

> **Initial-run exception:** The [workspaces module](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/modules/terraform-tfe-workspaces/main.tf) queues the first `tfe_workspace_run` separately from ordinary VCS-triggered runs. Its initial run may not require manual confirmation even with `auto_apply = false` -- this is exactly the setting on `rosa-boundary-prod-aws-creds` today, so its very first run was not necessarily gated the way its steady-state `auto_apply = false` suggests. Scaffold an empty root first, inspect any initial run and never rely on the normal manual gate for a newly registered workspace. Confirm the L2 settings have actually reconciled in HCP before approving changes to existing resources.

## Adding a workspace without breaking the chain

The meta-workspace currently manages **twelve** L3 workspaces across two AWS accounts -- six workspaces in the long-lived `rosa-boundary-stage` account, and six workspaces (credentials, account, two networks, and two regionals) in the now-parallel `rosa-boundary-prod` account. Treat the count as a snapshot, not a fixed total: production's `us-west-2` network/regional pair was itself added this way after the account, credentials, and `us-east-1` workspaces came online, completing parity with staging's two-region layout; a third region in either account would follow the identical procedure.

1. **Choose ownership:** new HCP project/team/policy or a new meta-workspace belongs in [infra-platform's ROSA tenant `projects` map](https://github.com/openshift-online/infra-platform/blob/main/hcp-terraform/tenants/rosa/main.tf). A new AWS workload inside the existing `rosa-boundary` project -- whether in the staging account, the production account, or a future third account -- belongs in the `workspaces` map of [`hcp-terraform/rosa-boundary/main.tf`](../../hcp-terraform/rosa-boundary/main.tf). Do not create a workspace manually as a substitute for its owner. Distinguish account-global IAM (`deploy/account/`, one state per AWS account), per-account OIDC credentials, network, and per-region runtime states.
2. **Scaffold first, register second:** merge the new working directory and minimal valid Terraform configuration into the connected repo's default branch **before** adding the workspace definition in a separate PR. A new VCS-connected workspace needs an initial completed run before PR webhook speculative plans work. L1's first run is manual; L2/L3 initial runs are queued by `tfe_workspace_run`, but cannot succeed if the working directory is absent. Specify the `cloud.tf` workspace name for control-plane/credentials directories as appropriate; choose a reviewed exact `terraform_version` compatible with `required_version` and pinned providers. The production `aws-creds`, `account`, network, and regional directories all followed exactly this pattern before their L2 entries existed -- none of them needed a new source directory, since each reuses the same `hcp-terraform/aws-creds/rosa-boundary-prod`, `deploy/account`, `deploy/network`, or `deploy/regional` tree staging already uses.
3. **Provision prerequisites before registration:** ensure GitHub App/repo access, project/team access, TFE token set if using the TFE provider, AWS account/provider guard, tags, appropriate region and network. For a new AWS account, bootstrap its **own** HCP OIDC/roles/variable set as above -- as production did in [`hcp-terraform/aws-creds/rosa-boundary-prod/main.tf`](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf). For a new workload workspace in an **existing** account, extend that account's `role_groups.default.projects.rosa-boundary.workspace_names` allowlist (staging: [`hcp-terraform/aws-creds/rosa-boundary-stage/main.tf`](../../hcp-terraform/aws-creds/rosa-boundary-stage/main.tf); production: [`hcp-terraform/aws-creds/rosa-boundary-prod/main.tf`](../../hcp-terraform/aws-creds/rosa-boundary-prod/main.tf)), apply/verify the credentials stack, then attach its generated set in the L2 entry -- exactly the sequence production's `us-west-2` network and regional workspaces already completed: their names appear in both the allowlist and the L2 map, and (unlike the credentials workspace) their runs auto-apply once queued.
4. **Add the L2 map entry by PR:** set unique name, VCS org/repo, working directory, Terraform version, `variable_set_names`, and an explicit `variables` list (possibly empty). Set `auto_apply`/`auto_apply_run_trigger` deliberately; their **default is true**. For a workspace that must not auto-apply (as `rosa-boundary-prod-aws-creds` currently does not), also consider `execution_mode = "remote"` as all six production entries do regardless of their own `auto_apply` setting. Set `source_workspaces` only for real cross-workspace run dependencies, and arrange a proper way to supply outputs as inputs: a run trigger does not transfer Terraform outputs -- both of production's regional workspaces received their network's `vpc_id`/`subnet_ids` as plain Git-managed variable values, not via a trigger. Put stage/region/account, image pins and other workload inputs in this Git-controlled list, not in ad hoc HCP workspace variable edits. For every network, account and regional workspace in either account, this map is the source of truth for variables; do not change them directly through HCP UI/API/MCP.
5. **Review both PR and initial/merge runs:** confirm speculative plans actually appeared on upstream branches; check initial-run history, variable set bindings, policy results, planned AWS account/region, and network inputs. After merge, verify the L2 apply created the workspace, the initial L3 run completed, and subsequent VCS and run-triggered plans/applies behave as intended. For a new account or region -- including confirming whether a newly registered production regional workspace has actually applied its concrete `vpc_id`/`subnet_ids` inputs -- validate live access, routing, audit and recovery rather than assuming staging credentials or VPC IDs generalize. Do not manually trigger/create/apply runs just to paper over a missing source directory, failed policy, or unsatisfied credential prerequisite.

## Prow and image delivery are separate from HCP permissions

Prow's pre-merge LocalStack/Lambda/Go CI is defined in [`openshift/release`](https://github.com/openshift/release/tree/master/ci-operator/config/openshift-online/rosa-boundary), with a test harness in [`tests/localstack/`](../../tests/localstack/). CI secrets are not HCP AWS credentials. Konflux builds Quay images, including the Boundary runtime and investigation Lambda; both staging and production pin image tags by commit in each region's **L2 variables**, requiring another reviewed HCP run for promotion. `container_image` and `lambda_image_tag` select different artifacts; updating the investigation Lambda pin does not update the Fargate runtime image or prove that any region has deployed the change. The **ROSA BOUNDARY CI GitHub App** supplies authenticated GitHub downloads to image builds; its build-secret path is distinct from the Terraform Cloud VCS GitHub App and from AWS plan/apply roles. See the [image build instructions](../../AGENTS.md) and [`build/github_dl.py`](../../build/github_dl.py) for the repository-owned requirements. Prow pre-merge LocalStack tests do **not** demonstrate that a separate nightly real-infrastructure job or Sippy reporting is deployed; verify such a job in `openshift/release` before asserting it exists.
