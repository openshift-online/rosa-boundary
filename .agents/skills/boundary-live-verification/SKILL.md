# Boundary live verification

Accept a **specific live-test objective** and a revision (working tree, commit/range, or PR). Coordinate with [boundary-change-verification](../boundary-change-verification/SKILL.md) for changed boundaries and safe local checks. This skill is the *explicitly authorized* live-dev follow-up, not permission to mutate AWS merely because a user asked which tests are necessary. Read [execution guide](references/execution.md) before a live run, plus current Makefiles, Terraform variables, CLI help/code, and the test's relevant implementation. Prefer the current repo over dated runbooks or contributor notes.

## 1. Plan, do not deploy yet

- Identify exact source to test. Never fetch/switch/reset to "latest" behind the user's back; do not mutate or sweep up unrelated work. For PR/historical revisions, use an authorized separate checkout. Record a source fingerprint covering relevant changed *tracked and untracked* files, or require a clean checkout; HEAD alone does not identify a dirty build. Check the container build context for unrelated local files before building. Classify CLI, image, Lambda (Zip vs Image), Terraform (account/network/regional), OIDC, runtime, and audit changes separately. Local checks remain the responsibility of the change-verification skill.
- Get an explicit test contract: expected result, allowed AWS account and region, approved target cluster/OCM endpoint, identity and ABAC preconditions, required evidence, time/cost bound, and cleanup behavior. Do not select a customer cluster, make an OCM/Bedrock request, create tasks, or read potentially sensitive transcripts merely to discover a target. Ask when these are missing.
- Discover a per-contributor profile using `scripts/dev_state.py`. Treat it as a hint, not as credentials or proof of permission. Never embed a shared Keycloak URL, account ID, thumbprint, role, or cluster in this skill. Obtain the issuer/base URL, realm, client ID, groups, thumbprint and approved cluster from contributor/operator configuration and live verification. Do not provision Keycloak users or copy passwords.
- Check ambient AWS identity with `aws sts get-caller-identity`, explicit region on every AWS request, profile account match, provider `allowed_account_ids`, local state ownership/backend, `.env` effective `TF_VAR_*` overrides versus tfvars, and existing AWS resources. Verify current CLI config is **dev**, or isolate `XDG_CONFIG_HOME` and `XDG_CACHE_HOME` for this profile and discover dev config afresh with `configure --environment dev`. Confirm all discovered ARNs and EFS/cluster IDs belong to the target before start/stop/close. Never run `make show-env`, print tfvars/state/secrets, or dump Lambda environment values or raw audit logs.
- Compare *observed* artifact provenance to the changeset: image architecture + registry digest (not just a mutable tag), ECS base definition and per-investigation definition, Lambda package type and deployed code/image hash, CLI binary revision/hash, Terraform plan and account/regional ownership. An image tag push does not update an existing task or prove a Lambda change deployed. When provenance cannot be established, mark mismatch/unknown and propose a rebuild/redeploy; do not claim reuse.
- Give the user a bounded action plan and request **explicit approval** for the target account/region, selected test and target cluster, image publication, each proposed Terraform apply, and investigation creation/cleanup. Treat approvals for one scope as insufficient for a later changed/destructive plan. Never automatically apply/destroy or use `deploy/regional/Makefile` for staging. If no mutations are needed, request authorization for the live investigation/test before creating it.

## 2. Reconcile the approved dev environment

Use [execution guide](references/execution.md) for ordered bootstrap and reuse gates. Run account IAM root before network/regional on a genuinely new account; do not import/adopt/transfer existing IAM ownership automatically. Inspect *all three* root Makefiles before invoking targets. Use root Makefile for container and CLI builds, verify actual architecture, and publish a revision-specific image/digest (avoid using mutable `latest` as proof). Configure image URI through approved gitignored local tfvars, and plan via the owning Makefile. Inspect a plan in full for account/region, replacement/deletion, OIDC/ABAC, cost and audit effects before `make apply`; Lambda Zip builds occur in regional `apply`. Never run the regional `lambda` target (`-target` and `-auto-approve`). No unattended destroy or overwrite of someone else's state. If changing infrastructure means changing account-wide Bedrock invocation logging, require separate review of that scope.

After apply, independently re-read AWS resource state and verify configuration is ACTIVE/Successful before running tasks. Verify task definition image/digest, actual Fargate architecture, Lambda code hash/package, roles/ABAC, and log/audit destinations. **A clean plan is not proof of behavior.** If drift or effective `.env` defaults would change IAM, disable overlays, or change ABAC, stop for review. A development deployment may reuse a shared externally operated Keycloak but the skill does not deploy it.

## 3. Run the test and leave evidence

- Build/use the requested CLI revision with isolated XDG config/cache, log in interactively as an authorized SRE (no password scripting). Verify discovered account, region, ECS cluster, roles, EFS and Lambda. Run only the agreed test. For a lifecycle smoke: `start-task` with a bounded timeout and unique investigation ID → save task ARN/ID → `join-task` as `sre` → write a harmless marker → exit Exec → `stop-task --wait` → check container sync warnings, session-log evidence and expected marker object under that task's S3 prefix with a separate audit-reader identity → `close-investigation --yes` **without** `--force` after all tasks stop. `exit` does not stop the task; STOPPED does not prove upload. Never print full logs/objects; record identifiers and existence checks only. Protect EFS and S3 from credentials/customer data.
- For identity isolation, credentials, OCM, Backplane, Bedrock or reaper tests, specify the extra principals/permissions, timeouts, negative assertions, API side effects, and cleanup separately. A smoke test cannot prove these boundaries. If a test fails halfway, stop and account for each task, then close only when safe. On uncertain sync, record failure and preserve evidence; do not suppress it with forced closure. Time-bounded tasks and reapers are fallback, not cleanup substitutes.
- Record each run's deployment snapshot and result with `scripts/dev_state.py`; store only identifiers and evidence *status*, not tokens, audit contents, plaintext config, or customer material. Re-read AWS on subsequent runs; a ledger entry is never authoritative. Report commands, exact tested revision/artifact digests, account/region/cluster, passed/failed/blocked/unverified boundaries, artifact evidence locations (not contents), lingering tasks/investigations and follow-up actions. Do not claim end-to-end success when any required audit evidence is missing.
