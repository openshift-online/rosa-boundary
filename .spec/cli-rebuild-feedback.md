# ROSA Boundary CLI rebuild: validation feedback

Status: **reviewed proposal with an additional terminology change pending review**, not an implementation authorization. This captures feedback from the CLI validation walkthrough and high-level approaches to discuss before changing the CLI. No runtime or deployment changes are authorized by this document.

## CLI-wide requirements

1. **Errors must be actionable.** Replace generic positional-argument errors such as `accepts 1 arg(s), received 0` with the missing argument's name, expected command syntax, and a pointer to that command's `--help`. Apply the same standard to extra arguments, invalid or missing flag values, and other user-correctable input errors across the command tree. Validation should happen before authentication or AWS mutations wherever possible. Do not dump the entire help page on every error.
2. **JSON means a JSON result on stdout.** For commands offering `-o json`, define a single valid JSON result on stdout, without progress text, prompts, or authentication events mixed in. Check stdout and stderr separately in tests; a terminal combines their display. Commands without a data result need an explicit JSON result contract. Resolve the treatment of interactive shell I/O before claiming that `session join` or `session start --connect` is wholly JSON-capable.
3. **Remove the `ROSA_BOUNDARY_AUTH_EVENT` protocol.** It was not requested and is an unexpected machine-readable stream on stderr. Keep necessary human-readable authentication challenges and errors, including device-approval instructions, on stderr without exposing tokens. A successful authentication event alone must not be mistaken for command success.
4. **Make terminal output scannable.** Clearly separate progress, a single success message, relevant identifiers, and the next suggested command; avoid duplicate success announcements, crowded semicolon-separated fields, and trailing spaces. Suggested commands should be copyable, include `--profile` when it selects the correct deployment, and omit region/ECS flags already provided by that profile. If an invocation depended on an unsaved override, preserve the override needed to target the same resource. Do not call a `--no-wait` task ready before it reaches RUNNING.
5. **Use the same lifecycle verbs for investigations and sessions: `create` / `close`.** Keep `investigation create` and `investigation close`; rename the session actions from `session start` to `session create` and from `session stop` to `session close`. Session creation may still create a new investigation workspace when no existing investigation is specified. Closing a session stops that task; it does **not** close its investigation or delete the reusable workspace. Leaving a joined shell still does not close the session, and task shutdown/audit verification remain distinct. Update command help, suggested commands, error recovery, docs, examples, tests, and any supported scripts together. Decide explicitly whether old verbs should be rejected with helpful migration guidance or temporarily accepted as aliases rather than leaving the public command contract ambiguous.

## Specific feedback

| Surface | Feedback and proposed direction |
| --- | --- |
| Boolean help | Display `--use-device-code` as an ordinary boolean flag, not `--use-device-code[=true\|false]`. Keep the ability to explicitly select false if a saved profile or environment preference selects device flow; supporting `=false` need not clutter the flag listing. Confirm which help output produced the bracketed form, since the binary in this checkout displays the bare flag. |
| `config list` with no profiles | Print a helpful no-profiles message with a pointer to `rosa-boundary config init --help` instead of succeeding silently. Treat a missing config and an empty profile set alike; still report malformed config as an error. |
| `config list` with profiles | Use the existing list-command table style: labeled columns and a separator (for example, `ACTIVE`, `PROFILE`, `ACCOUNT ID`, `ENVIRONMENT`, `REGION`), retaining the `*` active-profile marker. |
| `session --help` | Add four brief `session create` examples: create a session with a new auto-generated investigation ID; create a session in an existing investigation with `--investigation-id`; configure fresh OCM credentials in an existing session; create a session with a new investigation and `--with-credentials ocm`. Explain that OCM authorization may require separate approval and that credential injection cannot be paired with `--no-wait`. Examples should be illustrative, not silently select a real OCM environment. |
| `session create` result | After readiness (and OCM configuration when requested), show an explicit success message, the cluster/investigation and session ID, then `To join this session, run:` on its own line with a minimal, profile-qualified command. Avoid repeating metadata already shown in progress output. For `--no-wait`, distinguish launched from ready. |
| `session credentials configure/clear ocm` without session ID | When the session ID is omitted, discover eligible RUNNING sessions owned by the authenticated user in the selected deployment. If exactly one is found, show identifying details (session ID, cluster, investigation, status) and a suggested command; **do not automatically configure or clear credentials**. If none or several are eligible, provide actionable selection guidance without guessing or revealing other users' sessions. Include `--ocm-url` in the suggestion **only if the user supplied it**; otherwise retain normal environment selection behavior. Do not acquire OCM credentials merely to provide the suggestion. |
| `session close` confirmation | Put profile, account, region, session ID, cluster, investigation, and owner on separately labeled lines so the user can verify the exact target before confirming. Clearly state that closing this task leaves the investigation open. |
| `investigation create` result | Separate the progress block from an explicit, single success message and the access-point ID, then show `To create a session, run:` and the suggested command on its own line. Remove duplicated creation messages and unnecessary `--region` when saved in the profile. |

## Acceptance themes for the eventual change

- Test missing/extra arguments and invalid flags across command families, including named missing arguments and command-specific help pointers, without deleting existing tests.
- Exercise empty and populated profile lists, parent `session --help`, the four examples, and success/failure/no-wait wording.
- Separate stdout from stderr in JSON tests, including cached login, fresh browser/device approval, and failure paths. Verify human approval remains possible after removing auth events and that machine-readable results are valid JSON.
- Test zero, one, and multiple eligible credential sessions, ownership filtering, suggestion-only behavior, and whether supplied `--ocm-url` is preserved or omitted.
- Review suggested commands with saved settings versus unsaved deployment overrides; verify they target the intended profile and resource without redundant flags.
- Verify that the public `session create` / `session close` verbs and every generated follow-up or recovery command agree; closing a session must leave its investigation available, while investigation closure retains its own explicit cleanup and audit checks. Record the chosen old-verb compatibility policy and test it.

**Next step:** Review this list and settle any output-contract or interactive-command exceptions before deciding how to divide or implement the work. No CLI code changes are part of this proposal.
