# CLI Authentication Model

The Boundary CLI starts with an OIDC ID token from the configured identity provider, not pre-existing AWS credentials. For the current command-specific flow, check [`internal/cmd/root.go`](../../internal/cmd/root.go) and [`internal/aws/sts.go`](../../internal/aws/sts.go); IAM trust and ABAC are defined in [`deploy/account/`](../../deploy/account/) and [`deploy/regional/`](../../deploy/regional/). Consult the [user access guide](../runbooks/user-access-guide.md) for setup and the [investigation workflow](../runbooks/investigation-workflow.md) for an end-to-end check.

## Authentication steps

1. `rosa-boundary configure` can discover deployment configuration via Lambda after authenticating with OIDC and assuming an invoker role. It does **not** use existing config-file OIDC settings for auto-discovery. Supply the intended account, region, project and environment, and override OIDC flags for a non-default identity provider. Alternatively configure manually. `configure --use-device-code` uses headless device approval for discovery and saves `oidc_use_device_code: true`; without an explicit true flag it uses browser bootstrap and saves `false`, even if the old file or environment says true. `--auto-discover=false` saves the selected boolean without logging in. See [`internal/cmd/configure.go`](../../internal/cmd/configure.go).
2. `rosa-boundary login` uses browser authorization-code PKCE by default when a fresh Boundary ID token is needed. Device mode displays a verification URL and user code on stderr; an SRE approves on another device while the CLI waits, without opening a local browser or listening for a callback. A valid token is cached under `XDG_CACHE_HOME` and reused independent of selected flow until shortly before its actual JWT `exp`; `login --force` or global `--force-login` requests fresh authentication using the selected flow. STS rejection of a cached token can also trigger a fresh-login retry in that flow, with no automatic browser/device fallback. See [`internal/auth/token.go`](../../internal/auth/token.go). A cached ID token is not a standing AWS access key.
3. `start-task` and `create-investigation` assume the Lambda-invoker IAM role via `AssumeRoleWithWebIdentity`, using the OIDC token without an ambient AWS credential chain. The CLI calls Lambda with temporary SigV4 credentials; Lambda also validates the ID token and authorization claims before creating resources. `start-task` additionally assumes the SRE role to wait for and optionally connect to the new task. See [`internal/cmd/start_task.go`](../../internal/cmd/start_task.go) and [`lambda/create-investigation/handler.py`](../../lambda/create-investigation/handler.py).
4. Task management commands such as `join-task`, `list-tasks`, `stop-task`, `list-investigations`, and `close-investigation` also use an OIDC token to assume the shared SRE IAM role through STS on each CLI invocation. They do **not** use ambient workstation AWS credentials. The shared *role* issues distinct temporary sessions; it is not a shared secret. `join-task` hands ECS Exec to the AWS `session-manager-plugin` installed on the workstation.

AWS STS derives session tags from the token's `https://aws.amazon.com/tags` claim when the role trust permits tagging. IAM compares the caller's principal tag with the ECS task tag for the deployment's configured ABAC key; **do not assume that key is `username`**. A missing or mismatched claim may prevent STS assumption or ECS Exec. Lambda separately checks configured group membership and the ABAC claim. See the [architecture overview](overview.md), current IAM policies, and Lambda tests for deployment-specific behavior.

## Flow selection and headless approvals

For ordinary commands the effective device preference is explicit `--use-device-code=true|false` (bare flag means true) > `ROSA_BOUNDARY_OIDC_USE_DEVICE_CODE` > YAML boolean `oidc_use_device_code` in `${XDG_CONFIG_HOME:-$HOME/.config}/rosa-boundary/config.yaml` > default `false`. An explicit false selects browser login for **both** providers, overriding a saved true; malformed booleans fail instead of silently falling back. The preference selects a flow, not an issuer, shared token, or credential storage location. `configure` is the bootstrap/persistence **exception** described above: it only selects device mode if explicitly passed true, regardless of the environment or previous file.

Boundary uses its OIDC **ID token** for STS and Lambda; OCM credential injection uses a fresh **OCM access token** from its own issuer/client, transferred into task-scoped, audit-excluded storage. `start-task --with-credentials ocm` and `credentials configure ocm` follow the same device preference when they need OCM authentication, unless the invocation explicitly specifies `--ocm-auth-flow auth-code|device` or `--auth-flow auth-code|device`, respectively. These overrides apply to OCM **only**: `auth-code` requires a browser callback even when Boundary is headless; `device` never opens a local browser. One `start-task --with-credentials ocm` can therefore require **two separate human approvals**, one for Boundary and one for OCM. A cached Boundary token may remove its challenge but does not replace OCM approval.

## Authentication events for scripts

Authentication is per-user and **human-approved**, not unattended credential issuance. Use `-o json` / `--output json` on **each auth-bearing command** whose challenge a script needs to consume; a preflight `login -o json` does not guarantee the next command will not need fresh authentication. The output flag is local to auth-bearing leaf commands, not root or offline commands. The existing JSON result commands (`start-task`, `create-investigation`, `list-tasks`, `list-investigations`, `close-investigation`) keep their single result document on stdout. Status-only commands, including `login`, `configure`, `stop-task` and OCM credential commands, do not gain JSON results on stdout. `join-task` and `start-task --connect` use terminal session I/O, not machine-readable shell output; `start-task --connect` can emit its task result before connecting. In text mode authentication instructions go to stderr; in JSON mode each auth event is a **separate** immediately flushed stderr line prefixed `ROSA_BOUNDARY_AUTH_EVENT `, and other diagnostics may still appear on stderr. Do not parse all stderr as JSON or mistake an auth event for a successful operation.

```text
ROSA_BOUNDARY_AUTH_EVENT {"version":1,"provider":"boundary","event":"device_authorization","verification_uri":"https://...","user_code":"ABCD-EFGH","expires_in":600}
ROSA_BOUNDARY_AUTH_EVENT {"version":1,"provider":"boundary","event":"authenticated","source":"device"}
ROSA_BOUNDARY_AUTH_EVENT {"version":1,"provider":"ocm","event":"device_authorization","verification_uri":"https://...","user_code":"WXYZ-1234","expires_in":600}
ROSA_BOUNDARY_AUTH_EVENT {"version":1,"provider":"ocm","event":"authentication_failed","reason":"expired"}
```

Every event has `version` and `provider` (`boundary` or `ocm`). `device_authorization` precedes polling and carries `verification_uri`, `user_code`, and `expires_in` seconds. `authenticated` means only that a locally unexpired Boundary ID token or fresh OCM access token was obtained; `source` is `cache`, `device`, or `browser` (`cache` is Boundary-only). `authentication_failed` uses a sanitized reason (`denied`, `expired`, `canceled`, `network`, `invalid_response`, or `other`). A cached success can be followed by another Boundary attempt after STS rejection, then an OCM challenge. The **process exit code** determines overall command success; neither `authenticated` nor a task's creation proves downstream STS, credential transfer, or audit sync worked. Drain stderr **while the child is running** so the human can approve before expiry; do not wait for exit to read it. Treat the displayed short-lived user code and verification URL as sensitive operational output: share them only through an approved private channel, not shared CI logs or files. The OAuth `device_code` secret, tokens, token-response bodies, and PKCE verifiers must never be printed. See the [user access guide's script example](../runbooks/user-access-guide.md#script-driven-human-approved-login).

## Configuration and audit access

The CLI resolves settings from flags, environment, a config file and defaults; check [`internal/config/`](../../internal/config/) and CLI `--help` for current fields. The invoker role and Lambda name are needed to start a task, while management commands require an SRE role and `close-investigation` also needs the EFS filesystem ID. Auto-discovery populates these from the deployment when available.

The CLI's temporary SRE credentials are not exported to your shell. Independent `aws logs` or `aws s3` audit retrieval uses the AWS CLI and an **operator/audit-reader identity with read permissions** in the correct account and region. Neither pre-existing AWS CLI credentials nor AWS CLI installation is required for ordinary Boundary CLI operations. See [Verify Audit Evidence](../runbooks/investigation-workflow.md#verify-audit-evidence).
